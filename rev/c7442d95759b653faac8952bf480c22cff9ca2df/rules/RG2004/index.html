RG2004: Owned coverage must match the exact Lake inventory🔗

Development documentation generated from commit c7442d95759b with Lean 4.34.0; linter version unreleased (no released package). Moving route: /regula/dev/rules/RG2004/. Snapshot route for this commit: /regula/rev/c7442d95759b…/rules/RG2004/. Once this commit is published, its snapshot is kept by every later deployment. See versions and evidence.

Problem. The exact module and declaration inventory from Lake does not match the owned coverage: a claimed library imports an excluded or checker-probe module, a module is outside every manifested library, or ownership cannot be determined.

Action. Remove the forbidden import, or add the module to the intended claimed library's globs, so every owned module belongs to exactly one classified target.

What triggers it🔗

Module inventory comes from Lake's elaborated configuration and Lean's recorded module indices, not from file lists or name prefixes. The checker resolves each imported root-package module's origin and rejects unexpected project modules, imports of excluded modules into claimed ones, and unknown ownership (unexpected-project-module and related subreasons).

The impact depends on the subreason. A forbidden import or a module outside every manifested library (unexpected-project-module) is a violation (lake lint exit 1 unless the same run also has an incomplete finding). A configured module that was omitted or not freshly built, or a declaration attributed outside the claimed surface, is incomplete evidence (INCOMPLETE, lake lint exit 3).

Why it matters🔗

A conformance claim covers an exact set of modules. A module imported into a claimed library but outside every surface would contribute declarations nobody classified, and an umbrella import alone does not define that set.

How to fix it🔗

  1. Delete imports of excluded modules (for example checker or fixture modules) from claimed code.

  2. Use a glob with the intended meaning, such as .andSubmodules `Lib in lakefile.lean or ["Lib", "Lib.+"] in lakefile.toml, so every intended module is in the library.

  3. Classify any new root library or executable in the manifest (RG2002).

Required proof shape🔗

No proof obligation: the rule concerns the declaration inventory. The removed import must not have supplied evidence the claim still relies on.

What a passing result establishes🔗

The claimed modules are exactly Lake's configured modules for the claimed targets, and every owned constant is attributed to one of them.

It does not establish:

  • That the chosen library boundaries are the ones the project intends to claim; that is reviewed with the manifest rationale.

Review obligations the rule-coverage map associates with this rule (identifiers of the checker's Residual account):

  • R-QUALIFY: the checker's detection is qualified for this invocation, toolchain and capability

Every accepted result lists all residual obligations as open, whatever rules it checked: R-INTENT, R-INVARIANT, R-LAWS, R-BOUNDARY, R-NONVACUITY, R-DOC, R-COST, R-QUALIFY (and R-GRAPH for a serialized-graph claim). A listed identifier is an open obligation, never a completed review.

Every accepted result also relies on these trusted mechanisms (the checker's Trusted account), which no rule verifies:

  • toolchain: Lean elaborator, kernel and compiler at the snapshot's toolchain identity

  • acquisition: manifest parsing, Lake loading, and source, configuration and dependency acquisition

  • extraction: environment extraction, compiler and worker processes, and JSON transport

  • runtime: native runtime and every execution boundary reported as trusted

Configuration and exceptions🔗

No source option, attribute or command-line flag makes this rule pass on a claimed surface; an exclusion in the manifest never permits a claimed module to import the excluded one.

Project enforcement runs through lake lint (incremental), lake lint -- --fresh and lake exe axiomGate (fresh whole-project audits from empty build output), and the build-lint policy target. See the adoption guide.

Limitations and unsupported cases🔗

Whole-project scope only: the editor is explicitly partial and does not report this rule, and a single-file audit does not either.
