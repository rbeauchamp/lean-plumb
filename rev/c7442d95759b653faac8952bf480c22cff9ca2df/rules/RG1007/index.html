RG1007: Executable contracts require supported closed evidence🔗

Development documentation generated from commit c7442d95759b with Lean 4.34.0; linter version unreleased (no released package). Moving route: /regula/dev/rules/RG1007/. Snapshot route for this commit: /regula/rev/c7442d95759b…/rules/RG1007/. Once this commit is published, its snapshot is kept by every later deployment. See versions and evidence.

Problem. A closed ExecutableContract f R registration does not have the supported shape: it is not closed, it names no complete implementation constant, or the implementation is not an eligible executable definition.

Action. Register the named implementation itself and put its complete domain inside the predicate: theorem c : ExecutableContract f (fun g => ∀ x, P x (g x)).

What triggers it🔗

The checker recognizes declarations of type Regula.ExecutableContract f R as executable promises about f. It rejects, with applicability executable-contract, a registration with free parameters, a partially applied or term-parameterized implementation, or an implementation that is missing, noncomputable, unsafe, partial, proposition-valued, type-producing or not an executable definition.

Lean's type checker separately checks the supplied proof of R f.

Why it matters🔗

A contract is useful only if it constrains the code callers run. A registration over f n for a fixed parameter, or over an ineligible constant, says nothing about the executable definition across its domain.

How to fix it🔗

  1. Move the quantified parameters into the predicate: replace theorem c (n : Nat) : ExecutableContract (f n) (fun v => v = n) by theorem c : ExecutableContract f (fun g => ∀ n, g n = n).

  2. Name the computable, safe, non-partial definition that callers use; route callers through c.run.

  3. Universe-polymorphic implementations are supported; explicit universe instantiation is recorded.

Correction

Change to Fixture.lean:

  import Regula.Contract
  /-! Identity on natural numbers, with its full-domain contract. -/
  def identity (n : Nat) : Nat := n
- theorem contract (n : Nat) : Regula.ExecutableContract (identity n) (fun value => value = n) := ⟨rfl⟩
+ theorem contract : Regula.ExecutableContract identity (fun f => ∀ n, f n = n) := ⟨fun _ => rfl⟩

The correction moves the complete natural-number domain inside the identity contract's predicate, retaining the same pointwise equality.

Required proof shape🔗

ExecutableContract f R for a named constant f with R : type-of-f → Prop stating the full-domain requirement. The proof inhabits exactly R f; a weaker R changes the requirement and is a review failure.

What a passing result establishes🔗

The registration is closed, names an eligible executable constant, and Lean checked a proof of the stated predicate about it.

It does not establish:

  • That R expresses the intended behavior (R-INTENT) and that every caller uses the contracted implementation (R-INVARIANT). Every accepted account lists these as open for each reported contract.

  • Behavior of compiled code beyond the Lean definition; execution boundaries are RG3001 and RG3002.

Review obligations the rule-coverage map associates with this rule (identifiers of the checker's Residual account):

  • R-INTENT: the proposition expresses the intended requirement, with its quantifiers, hypotheses and limits

  • R-INVARIANT: the intended invariants, write paths and callers are all covered by proof-bearing interfaces

  • R-QUALIFY: the checker's detection is qualified for this invocation, toolchain and capability

Every accepted result lists all residual obligations as open, whatever rules it checked: R-INTENT, R-INVARIANT, R-LAWS, R-BOUNDARY, R-NONVACUITY, R-DOC, R-COST, R-QUALIFY (and R-GRAPH for a serialized-graph claim). A listed identifier is an open obligation, never a completed review.

Every accepted result also relies on these trusted mechanisms (the checker's Trusted account), which no rule verifies:

  • toolchain: Lean elaborator, kernel and compiler at the snapshot's toolchain identity

  • acquisition: manifest parsing, Lake loading, and source, configuration and dependency acquisition

  • extraction: environment extraction, compiler and worker processes, and JSON transport

  • runtime: native runtime and every execution boundary reported as trusted

Configuration and exceptions🔗

No source option, attribute or command-line flag makes this rule pass on a claimed surface. set_option linter.regula false and regula.localFoundation never waive it: lake lint, the build-lint policy target and axiomGate still apply the rule. Where Regula's local linter reports a finding during a project build (axiomGate and the policy target keep it on by default; lake lint builds with it off, whatever the source sets linter.regula to), that finding is a build warning, so the result is INCOMPLETE under RG2003 instead of carrying this rule's finding. Switching the local linter off changes which finding is reported, never whether the result is accepted. Hiding the diagnostic does not establish the property it checks.

Project enforcement runs through lake lint (incremental), lake lint -- --fresh and lake exe axiomGate (fresh whole-project audits from empty build output), and the build-lint policy target. See the adoption guide.

Limitations and unsupported cases🔗

Term-parameterized and partial-application registrations are unsupported shapes, not proofs of incorrectness; restate them as closed full-domain contracts.
