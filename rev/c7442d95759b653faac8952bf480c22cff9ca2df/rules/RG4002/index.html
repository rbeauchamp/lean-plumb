RG4002: Positive examples require warning-free elaboration and admission🔗

Development documentation generated from commit c7442d95759b with Lean 4.34.0; linter version unreleased (no released package). Moving route: /regula/dev/rules/RG4002/. Snapshot route for this commit: /regula/rev/c7442d95759b…/rules/RG4002/. Once this commit is published, its snapshot is kept by every later deployment. See versions and evidence.

Problem. A positive Lean fence in the documentation did not elaborate verbatim and warning-free, or it did and then failed admission or the declaration and axiom rules.

Action. Make the example correct as printed: fix its errors or warnings, and make its declarations satisfy the same rules as project code.

What triggers it🔗

Each positive fence is elaborated exactly as printed, with no inserted imports or wrappers, against a fresh build of the claimed libraries. It must be warning-free, pass checked admission, and pass the declaration and axiom rules under Standard-Logical. The fence failure is reported here together with the underlying finding (for example RG1001 for an axiom in the example).

A fence that fails without a source diagnostic (for example a worker that stopped before completing) is reported as INCOMPLETE, not as a violation.

Why it matters🔗

Readers copy documented examples and trust them. A positive example that does not elaborate, or that proves its claim with an axiom, teaches a false claim.

How to fix it🔗

  1. Fix the underlying finding shown with this diagnostic (for example prove the statement instead of declaring an axiom).

  2. If the example is meant to fail, mark it with an exact lean-fail marker instead (RG4003).

  3. Import what the example needs inside the fence; the checker inserts nothing.

Checked policy rejection: the violating input was completed by the checker and rejected with the findings below; the corrected input passed a completed positive check.

RG1001 error violation documentation example, claim standard-logical

Declaration reflexive at docs/Example.md:1#lean-snippet, line 2, column 7

project-axiom: reflexive axioms=[`reflexive]

Correction

Change to docs/Example.md:

  ```lean
  /-! Reflexivity for every natural number. -/
- axiom reflexive (n : Nat) : n = n
+ theorem reflexive (n : Nat) : n = n := rfl
  ```

The correction proves the same reflexivity claim in the positive fence; the violation reports the RG1001 underlying rejection alongside RG4002.

Required proof shape🔗

The fence proves exactly the claim the surrounding prose states. A narrower foundation or an execution claim in the prose needs its own evidence; fence success establishes only Standard-Logical admission.

What a passing result establishes🔗

The positive fence elaborated verbatim, warning-free, passed owned admission and the declaration and axiom rules.

It does not establish:

  • That the prose describes the fence faithfully (R-DOC, R-INTENT), or any narrower foundation claim.

Review obligations the rule-coverage map associates with this rule (identifiers of the checker's Residual account):

  • R-INTENT: the proposition expresses the intended requirement, with its quantifiers, hypotheses and limits

  • R-QUALIFY: the checker's detection is qualified for this invocation, toolchain and capability

Every accepted result lists all residual obligations as open, whatever rules it checked: R-INTENT, R-INVARIANT, R-LAWS, R-BOUNDARY, R-NONVACUITY, R-DOC, R-COST, R-QUALIFY (and R-GRAPH for a serialized-graph claim). A listed identifier is an open obligation, never a completed review.

Every accepted result also relies on these trusted mechanisms (the checker's Trusted account), which no rule verifies:

  • toolchain: Lean elaborator, kernel and compiler at the snapshot's toolchain identity

  • acquisition: manifest parsing, Lake loading, and source, configuration and dependency acquisition

  • extraction: environment extraction, compiler and worker processes, and JSON transport

  • runtime: native runtime and every execution boundary reported as trusted

Configuration and exceptions🔗

No marker makes a failing positive example acceptable; changing it to lean-fail changes what the documentation claims.

Run lake exe docFenceAudit (or ./scripts/verify.sh docs in this repository).

Limitations and unsupported cases🔗

Examples are checked under the declared toolchain only.
