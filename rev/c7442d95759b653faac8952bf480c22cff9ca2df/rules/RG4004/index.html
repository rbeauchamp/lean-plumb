RG4004: Teaching examples require authenticated compiler classification🔗

Development documentation generated from commit c7442d95759b with Lean 4.34.0; linter version unreleased (no released package). Moving route: /regula/dev/rules/RG4004/. Snapshot route for this commit: /regula/rev/c7442d95759b…/rules/RG4004/. Once this commit is published, its snapshot is kept by every later deployment. See versions and evidence.

Problem. A fence marked lean-trusted-compiler did not elaborate warning-free with an authenticated compiler-trusting declaration: it contains no native proof, or authentication failed.

Action. Use the marker only for an example that demonstrates native_decide (or another authenticated compiler-trusting mechanism); otherwise remove it.

What triggers it🔗

A teaching fence must elaborate warning-free and the checker must authenticate at least one compiler-trusting declaration in it, using the same fresh-frontend evidence as RG1004. If none is found, or authentication fails, the fence is rejected with applicability trusted-example.

The fence is also rejected, with the underlying finding, when any declaration in it fails the declaration rules under the teaching request (for example RG1001 for an axiom or RG1006 for an unsafe or partial declaration).

Why it matters🔗

Conforming claims reject compiler-trusting proofs (RG1004). A teaching fence is how the documentation shows one: it is classified and never counts as a conforming positive. A marker on an ordinary example would hide it from positive checking.

How to fix it🔗

  1. Remove the marker from an example that is an ordinary kernel proof; it is then checked as a positive example.

  2. For a genuine teaching example, keep the native_decide proof and import only the module that provides it (for example import Init).

The correction labels the same kernel proof as a positive example rather than as native teaching.

Required proof shape🔗

No proof obligation: the example demonstrates a compiler-trusting mechanism and is excluded from conforming evidence.

What a passing result establishes🔗

The teaching fence elaborated warning-free and contains an authenticated compiler-trusting declaration.

It does not establish:

  • Any conformance of the teaching example; it is classified, never counted as a positive proof.

Review obligations the rule-coverage map associates with this rule (identifiers of the checker's Residual account):

  • R-QUALIFY: the checker's detection is qualified for this invocation, toolchain and capability

Every accepted result lists all residual obligations as open, whatever rules it checked: R-INTENT, R-INVARIANT, R-LAWS, R-BOUNDARY, R-NONVACUITY, R-DOC, R-COST, R-QUALIFY (and R-GRAPH for a serialized-graph claim). A listed identifier is an open obligation, never a completed review.

Every accepted result also relies on these trusted mechanisms (the checker's Trusted account), which no rule verifies:

  • toolchain: Lean elaborator, kernel and compiler at the snapshot's toolchain identity

  • acquisition: manifest parsing, Lake loading, and source, configuration and dependency acquisition

  • extraction: environment extraction, compiler and worker processes, and JSON transport

  • runtime: native runtime and every execution boundary reported as trusted

Configuration and exceptions🔗

There is no name-based allowlist for native proofs; authentication is required for every teaching fence.

Limitations and unsupported cases🔗

Teaching fences are re-elaborated for authentication, so their imports are paid twice; keep them small.
