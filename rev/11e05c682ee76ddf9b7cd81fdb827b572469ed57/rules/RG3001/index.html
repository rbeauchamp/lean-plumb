RG3001: Execution closure must have no unresolved paths🔗

Development documentation generated from commit 11e05c682ee7 with Lean 4.34.0; linter version unreleased (no released package). Moving route: /regula/dev/rules/RG3001/. Snapshot route for this commit: /regula/rev/11e05c682ee7…/rules/RG3001/. Once this commit is published, its snapshot is kept by every later deployment. See versions and evidence.

Requirement. Every path in an executable root's execution closure resolves; no metaprogram hides replacement history.

Problem. The conservative execution closure of an executable root has a path the checker could not resolve: a missing compiled body, unavailable replacement history, an unsupported evaluator, or a cycle of replacement edges. The execution claim is INCOMPLETE.

Action. Remove the construction that prevents the analysis (for example a metaprogramming command such as run_cmd in the module), or make the missing compiled code available, then rerun.

What triggers it🔗

For every owned executable root the checker follows retained compiler edges, logical value dependencies, csimp candidates, observed implemented_by choices and partial helpers. Anything it cannot resolve or classify is reported with applicability execution-unresolved and impact incomplete, in both report and checked execution modes.

Replacement history is reconstructed by fresh re-elaboration; metaprogramming commands such as run_cmd, run_elab or module-local elaborators make it unavailable.

Why it matters🔗

An execution account that silently skipped an unresolved path would overstate what the compiled program is known to run.

How to fix it🔗

  1. Remove metaprogramming commands from modules whose implemented_by history must be authenticated, or move them elsewhere.

  2. Ensure every dependency's compiled code is available in the build.

  3. Break cycles consisting only of replacement edges.

Required proof shape🔗

No proof obligation for this rule; once resolved, checked execution may require correspondence proofs (RG3002).

What a passing result establishes🔗

Every path in each owned executable root's conservative closure was resolved and classified; an unresolved path is incomplete and never accepted.

It does not establish:

  • That the conservative closure is the program's actual runtime call graph: candidates and historical choices overapproximate it, and a safe program can be rejected.

Review obligations the rule-coverage map associates with this rule (identifiers of the checker's Residual account):

  • R-QUALIFY: the checker's detection is qualified for this invocation, toolchain and capability

  • R-INVARIANT: the intended invariants, write paths and callers are all covered by proof-bearing interfaces

  • R-INTENT: the proposition expresses the intended requirement, with its quantifiers, hypotheses and limits

Every accepted result lists all residual obligations as open, whatever rules it checked: R-INTENT, R-INVARIANT, R-LAWS, R-BOUNDARY, R-NONVACUITY, R-DOC, R-COST, R-QUALIFY (and R-GRAPH for a serialized-graph claim). A listed identifier is an open obligation, never a completed review.

Every accepted result also relies on these trusted mechanisms (the checker's Trusted account), which no rule verifies:

  • toolchain: Lean elaborator, kernel and compiler at the snapshot's toolchain identity

  • acquisition: manifest parsing, Lake loading, and source, configuration and dependency acquisition

  • extraction: environment extraction, compiler and worker processes, and JSON transport

  • runtime: native runtime and every execution boundary reported as trusted

Configuration and exceptions🔗

No execution mode waives an unresolved path.

Project enforcement runs through lake lint (incremental), lake lint -- --fresh and lake exe axiomGate (fresh whole-project audits from empty build output), and the build-lint policy target. See the adoption guide.

Limitations and unsupported cases🔗

This page's example is a diagnostic demonstration: the violating run is INCOMPLETE by design and is not accepted negative evidence. Its corrected counterpart passed a completed positive check.

The editor does not analyze execution: it reports neither this rule nor a pending notice for it. Only lake lint, axiomGate (including --file) and the build-lint policy target do.
