RG4003: Negative examples require completed intended rejection🔗

Development documentation generated from commit 11e05c682ee7 with Lean 4.34.0; linter version unreleased (no released package). Moving route: /regula/dev/rules/RG4003/. Snapshot route for this commit: /regula/rev/11e05c682ee7…/rules/RG4003/. Once this commit is published, its snapshot is kept by every later deployment. See versions and evidence.

Requirement. A lean-fail fence fails to elaborate with one error message that matches its whole pattern.

Problem. A fence marked lean-fail did not fail as specified: it elaborated successfully, failed for a different reason, or the worker crashed or timed out.

Action. Make the example fail for exactly the documented reason, adjust the pattern to match one real error message, or remove the marker if the example is valid.

What triggers it🔗

A negative fence must complete with a source rejection, and one effective error message must match the entire expected pattern. Informational output, a pattern matched across several messages, a crash, a timeout or a successful elaboration does not pass.

An example that elaborated successfully or failed with a non-matching message is a violation; a worker that crashed, timed out or did not complete is INCOMPLETE.

Why it matters🔗

A negative example documents what Lean rejects. If it stops failing, or fails for another reason, the documentation claims a rejection that no longer holds.

How to fix it🔗

  1. If the example is actually valid, remove the lean-fail marker so it is checked as positive.

  2. If it should fail, edit the example so it fails for the documented reason, and write a pattern that matches that one error message.

  3. Keep patterns to literal fragments joined by .* and alternatives separated by |.

Required proof shape🔗

No proof obligation: the example demonstrates a rejection. Its pattern is part of the claim and is reviewed with the prose.

What a passing result establishes🔗

The negative fence completed with a source rejection whose single error message matches the whole pattern.

It does not establish:

  • That the rejection happens for the conceptual reason the prose explains beyond the matched message text.

Review obligations the rule-coverage map associates with this rule (identifiers of the checker's Residual account):

  • R-QUALIFY: the checker's detection is qualified for this invocation, toolchain and capability

  • R-DOC: documentation is complete and faithful to the declarations and requirements

Every accepted result lists all residual obligations as open, whatever rules it checked: R-INTENT, R-INVARIANT, R-LAWS, R-BOUNDARY, R-NONVACUITY, R-DOC, R-COST, R-QUALIFY (and R-GRAPH for a serialized-graph claim). A listed identifier is an open obligation, never a completed review.

Every accepted result also relies on these trusted mechanisms (the checker's Trusted account), which no rule verifies:

  • toolchain: Lean elaborator, kernel and compiler at the snapshot's toolchain identity

  • acquisition: manifest parsing, Lake loading, and source, configuration and dependency acquisition

  • extraction: environment extraction, compiler and worker processes, and JSON transport

  • runtime: native runtime and every execution boundary reported as trusted

Configuration and exceptions🔗

The marker and its pattern are the configuration; there is no option that accepts a non-failing negative example.

Limitations and unsupported cases🔗

Regula policy rejections of documentation examples can follow successful elaboration; this rule concerns compiler rejection patterns of lean-fail fences.
