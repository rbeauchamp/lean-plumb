RG1006: Unsafe and partial declarations require exact helper authentication🔗

Development documentation generated from commit 11e05c682ee7 with Lean 4.34.0; linter version unreleased (no released package). Moving route: /regula/dev/rules/RG1006/. Snapshot route for this commit: /regula/rev/11e05c682ee7…/rules/RG1006/. Once this commit is published, its snapshot is kept by every later deployment. See versions and evidence.

Requirement. Claimed modules declare nothing unsafe or partial; recursion is structural or proved terminating.

Problem. An owned declaration is marked unsafe or partial and is not the exactly authenticated code-generation helper of a safe recursive definition.

Action. Write a safe, terminating definition (structural recursion or termination_by), or move the unsafe/partial code out of the claimed surface.

What triggers it🔗

Authored unsafe and partial declarations are escape hatches: an unsafe declaration is checked only in Lean's unsafe mode, cannot be used by safe declarations or proofs and is not replayed as logical evidence, and a partial definition has no termination proof. They are rejected with applicability escape-hatch.

The only exception is the range-less partial helper Lean generates for a safe, termination-checked recursive def, admitted when every condition of standard §8.4 holds, including fresh-frontend attribution of the exact source.

Why it matters🔗

A positive proof surface must consist of kernel-checked definitions. Unsafe and partial code can be executed, but it cannot serve as logical evidence, and reasoning about it silently depends on its runtime behavior.

How to fix it🔗

  1. Remove an unnecessary unsafe marker.

  2. Replace partial def by a definition with structural recursion or a termination_by measure and decreasing_by proof.

  3. If the computation must stay unsafe or partial, move it to a separate, unclaimed dependency package; a claimed module cannot import an excluded module of its own package (RG2004). Where a claimed executable reaches it, it is reported as a trusted unsafe-computation or partial-computation boundary, which fails under checked execution (RG3002).

Required proof shape🔗

A total replacement keeps the same domain and result type; if it changes behavior, state and prove the relation to the intended function.

What a passing result establishes🔗

No authored unsafe or partial declaration is on the claimed surface; every admitted generated helper satisfied all §8.4 conditions.

It does not establish:

  • That unsafe or partial code elsewhere is logically unsound; the rule concerns evidence, not a claim that such code is wrong.

  • Termination proofs' adequacy for cost claims.

Review obligations the rule-coverage map associates with this rule (identifiers of the checker's Residual account):

  • R-QUALIFY: the checker's detection is qualified for this invocation, toolchain and capability

  • R-COST: cost claims name their domain and rest on an argument or bounded observation

  • R-INTENT: the proposition expresses the intended requirement, with its quantifiers, hypotheses and limits

Every accepted result lists all residual obligations as open, whatever rules it checked: R-INTENT, R-INVARIANT, R-LAWS, R-BOUNDARY, R-NONVACUITY, R-DOC, R-COST, R-QUALIFY (and R-GRAPH for a serialized-graph claim). A listed identifier is an open obligation, never a completed review.

Every accepted result also relies on these trusted mechanisms (the checker's Trusted account), which no rule verifies:

  • toolchain: Lean elaborator, kernel and compiler at the snapshot's toolchain identity

  • acquisition: manifest parsing, Lake loading, and source, configuration and dependency acquisition

  • extraction: environment extraction, compiler and worker processes, and JSON transport

  • runtime: native runtime and every execution boundary reported as trusted

Configuration and exceptions🔗

No source option, attribute or command-line flag makes this rule pass on a claimed surface. set_option linter.regula false and regula.localFoundation never waive it: lake lint, the build-lint policy target and axiomGate still apply the rule. Where Regula's local linter reports a finding during a project build (axiomGate and the policy target keep it on by default; lake lint builds with it off, whatever the source sets linter.regula to), that finding is a build warning, so the result is INCOMPLETE under RG2003 instead of carrying this rule's finding. Switching the local linter off changes which finding is reported, never whether the result is accepted. Hiding the diagnostic does not establish the property it checks.

partial_fixpoint helpers are not covered by the recursive-helper exception.

Project enforcement runs through lake lint (incremental), lake lint -- --fresh and lake exe axiomGate (fresh whole-project audits from empty build output), and the build-lint policy target. See the adoption guide.

Limitations and unsupported cases🔗

The helper exception is conservative: elaborators defined in the audited module, run_tac or by_elab in the recursion's proofs make the checker reject a definition Lean accepts.

Editor feedback may be pending until the project command completes the fresh-frontend check.
