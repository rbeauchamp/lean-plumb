RG1004: Compiler-trusting proofs require separate classification🔗

Development documentation generated from commit 11e05c682ee7 with Lean 4.34.0; linter version unreleased (no released package). Moving route: /regula/dev/rules/RG1004/. Snapshot route for this commit: /regula/rev/11e05c682ee7…/rules/RG1004/. Once this commit is published, its snapshot is kept by every later deployment. See versions and evidence.

Requirement. Claimed declarations use no compiler-trusting proof: no native_decide, Lean.trustCompiler, Lean.ofReduceBool or Lean.ofReduceNat.

Problem. A declaration on a positive surface depends on a compiler-trusting axiom: a native-proof axiom generated by native_decide, or Lean's built-in Lean.trustCompiler, Lean.ofReduceBool or Lean.ofReduceNat. Its proof trusts compiled code and the Lean compiler, not the kernel.

Action. Prove the same statement with a kernel-checked proof, for example decide (kernel reduction), rfl or an ordinary proof.

What triggers it🔗

native_decide evaluates a decision procedure with compiled code and adds an axiom asserting the result. When the checker authenticates that axiom and its parent (exact axiom type @decide P inst = true, exact parent proof, native replay and fresh-frontend origin), both are classified compiler-trusting and rejected with applicability compiler-trusting. The built-in axioms Lean.trustCompiler, Lean.ofReduceBool and Lean.ofReduceNat in a transitive axiom set are compiler-trusting by their exact identity.

Final environment metadata cannot authorize a generated native-proof axiom; fresh re-elaboration of the exact source establishes it. An unauthenticated axiom that only looks native is not compiler-trusting.

Why it matters🔗

Compiled evaluation is outside the kernel's checking. A compiler or runtime defect could make a false proposition "proved". Compiler-trusting is therefore not one of the three logical labels and never counts as conforming evidence.

How to fix it🔗

  1. Replace by native_decide with by decide when kernel reduction of the decision procedure is feasible.

  2. Otherwise give a structural proof, or prove a smaller lemma that decide can handle and combine the pieces.

  3. If the example exists only to teach the mechanism, keep it in documentation as a trusted-compiler teaching fence (RG4004), never on a claimed surface.

Correction

- /-! The concrete equality uses native proof evaluation. -/

+ /-! The same concrete equality has a kernel proof. -/

The correction proves the same concrete equality (2 : Nat) = 2 by rfl. The violation reports both the generated axiom and its parent theorem.

Required proof shape🔗

The replacement proof proves the same proposition. Kernel reduction (decide, rfl) is permitted, subject to the surface's foundation profile.

What a passing result establishes🔗

No positive declaration depends on a compiler-trusting axiom: an authenticated native-proof axiom or the built-in Lean.trustCompiler, Lean.ofReduceBool or Lean.ofReduceNat.

It does not establish:

  • Performance of the kernel replacement proof; cost claims are separate (R-COST).

Review obligations the rule-coverage map associates with this rule (identifiers of the checker's Residual account):

  • R-QUALIFY: the checker's detection is qualified for this invocation, toolchain and capability

  • R-COST: cost claims name their domain and rest on an argument or bounded observation

Every accepted result lists all residual obligations as open, whatever rules it checked: R-INTENT, R-INVARIANT, R-LAWS, R-BOUNDARY, R-NONVACUITY, R-DOC, R-COST, R-QUALIFY (and R-GRAPH for a serialized-graph claim). A listed identifier is an open obligation, never a completed review.

Every accepted result also relies on these trusted mechanisms (the checker's Trusted account), which no rule verifies:

  • toolchain: Lean elaborator, kernel and compiler at the snapshot's toolchain identity

  • acquisition: manifest parsing, Lake loading, and source, configuration and dependency acquisition

  • extraction: environment extraction, compiler and worker processes, and JSON transport

  • runtime: native runtime and every execution boundary reported as trusted

Configuration and exceptions🔗

No source option, attribute or command-line flag makes this rule pass on a claimed surface. set_option linter.regula false and regula.localFoundation never waive it: lake lint, the build-lint policy target and axiomGate still apply the rule. Where Regula's local linter reports a finding during a project build (axiomGate and the policy target keep it on by default; lake lint builds with it off, whatever the source sets linter.regula to), that finding is a build warning, so the result is INCOMPLETE under RG2003 instead of carrying this rule's finding. Switching the local linter off changes which finding is reported, never whether the result is accepted. Hiding the diagnostic does not establish the property it checks.

Authenticated native proofs are reported separately in documentation teaching mode (lean-trusted-compiler fences) and remain excluded from conforming positives.

Project enforcement runs through lake lint (incremental), lake lint -- --fresh and lake exe axiomGate (fresh whole-project audits from empty build output), and the build-lint policy target. See the adoption guide.

Limitations and unsupported cases🔗

The editor may defer authentication and report a pending result; the project command completes it.

An unauthenticated axiom that merely looks native is not compiler-trusting; it is rejected as an unknown axiom (RG1003) or project axiom (RG1001).
